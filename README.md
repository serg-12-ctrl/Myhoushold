# Бэкенд-сервис «Менеджер домашних запасов»

Мощный бэкенд-сервис на базе Django REST Framework для интеллектуального управления домашними продуктами и бытовыми товарами с учетом партий, сроков годности, автоматического прогнозирования и пессимистических транзакционных блокировок.

---

## 1. Архитектура и Структура проекта

Проект построен по принципу тонких контроллеров (Views) и выделенного сервисного слоя (Services), что изолирует бизнес-логику от HTTP-слоя и делает код легко тестируемым.

```text
myproject/
├── myenv/                  # Изолированное виртуальное окружение Python
├── manage.py               # Главный скрипт управления Django
├── pytest.ini              # Конфигурация тестовой среды Pytest
├── requirements.txt        # Список зависимостей проекта
├── Dockerfile              # Инструкция сборки Docker-образа приложения
├── docker-compose.yml      # Манифест оркестрации (Django, Postgres, Redis, Celery)
│
├── myproject/              # Системный пакет настроек проекта
│   ├── settings.py         # Конфигурация проекта (БД, JWT, Celery, Схемы ошибок)
│   ├── urls.py             # Корневой маршрутизатор (включает /docs)
│   └── celery.py           # Инициализация и расписание Celery Beat
│
└── myhousehold/            # Основное веб-приложение (Бизнес-логика)
    ├── migrations/         # История миграций базы данных
    ├── models.py           # Модели данных (Product, Batch, Operation, ShoppingItem, Notification)
    ├── services.py         # Сервисный слой (Бизнес-логика: FEFO, Идемпотентность, Аналитика)
    ├── views.py            # API Контроллеры (Продукты, Списки, Авторизация)
    ├── serializers.py      # Валидация JSON и сериализация данных
    ├── exceptions.py       # Глобальный стандартизированный обработчик ошибок (Раздел 16)
    ├── tasks.py            # Периодические и фоновые задачи Celery (Раздел 10)
    └── test_stock.py       # Юнит-тестирование всех 17 обязательных сценариев ТЗ
```

## 2. Модель данных (ERD)

Система оперирует пятью связанными сущностями:
1. **User (Пользователь):** Системная модель Django. Все данные строго изолированы в разрезе пользователей.
2. **Product (Товар):** Описывает тип продукта (название, категория, минимальный остаток, базовая единица измерения).
3. **Batch (Партия товара):** Ключевой элемент. Позволяет хранить один товар несколькими партиями с индивидуальными ценами, местами хранения (`fridge`, `pantry` и т.д.) и разными сроками годности `expires_at`.
4. **Operation (Журнал операций):** Неудаляемый лог любого изменения остатков (`purchase`, `consume`, `discard`, `correction`). Содержит `idempotency_key`.
5. **ShoppingItem (Список покупок):** Записи элементов для закупки. Могут добавляться вручную или автоматически воркером при дефиците.
6. **Notification (Уведомления):** Системный лог предупреждений о порче, просрочке или дефиците.

## 3. Инструкция по локальному запуску и настройке

### Настройка переменных окружения (`.env`)
Для локального запуска проект по умолчанию использует безопасную базу данных **SQLite3**. При развертывании в Docker-контейнере параметры автоматически переключаются на высокопроизводительный **PostgreSQL** через системные переменные окружения, заданные в `docker-compose.yml`:
* `POSTGRES_DB` — имя базы данных (дефолт: `myhousehold_db`)
* `POSTGRES_USER` — пользователь БД (дефолт: `db_user`)
* `POSTGRES_PASSWORD` — пароль доступа (дефолт: `db_password`)
* `DB_HOST` — сетевой хост базы данных (`db` внутри Docker, `localhost` локально)

### Локальный запуск без Docker:
1. Активируйте ваше виртуальное окружение:
   ```powershell
   .\myenv\Scripts\activate
   ```
2. Установите зависимости проекта:
   ```powershell
   pip install -r requirements.txt
   ```
3. Запустите миграции для создания структуры таблиц:
   ```powershell
   python manage.py migrate
   ```
4. Запустите локальный веб-сервер разработки:
   ```powershell
   python manage.py runserver
   ```
5. Проект станет доступен по адресу: `http://127.0.0`

### Запуск автоматических тестов:
Для верификации всех бизнес-сценариев выполните команду:
```powershell
python -m pytest
```

## 5. Описание ключевых алгоритмов и механизмов

### Алгоритм списания партий (Стратегия FEFO)
При вызове метода расхода `consume` с флагом `expires_first` система запрашивает партии товара, отсортированные по возрастанию даты `expires_at` (партии с пустым сроком годности уходят в самый конец). Списание происходит каскадно: если первой партии не хватает для закрытия объема, она обнуляется, фиксируется лог операции, и алгоритм переходит к следующей партии до полного погашения запроса.

### Алгоритм прогнозирования расхода запасов
Прогноз рассчитывается на основании скользящего временного окна (по умолчанию 14 дней):
1. Извлекаются все операции типа `consume` за этот период.
2. Применяется фильтрация аномалий: вычисляется медиана объемов списаний, и разовые крупные списания, превышающие 4 медианы, отсекаются.
3. Рассчитывается средний дневной расход `V = Сумма_Объемов / 14` дней (что корректно учитывает дни без расхода).
4. Оставшиеся дни жизни рассчитываются как `Текущий_Суммарный_Остаток / V`. При нехватке данных возвращается метрика `insufficient_data`.

### Правила формирования рекомендаций
Движок аналитики при запросе `GET /recommendations` налету сопоставляет данные:
* `use_soon` (Высокий приоритет) — если до окончания `expires_at` партии осталось менее 3 дней.
* `buy` (Средний/Высокий) — если текущий суммарный остаток равен 0, упал ниже `minimum_stock` или если согласно прогнозу товар истощится быстрее, чем за 3 дня.
* `waste_risk` (Высокий) — если текущий остаток конкретной партии превышает математически прогнозируемое потребление до даты её просрочки (`Остаток > Скорость_Расход * Дней_До_Просрочки`).

### Механизм обеспечения идемпотентности
Для защиты от повторного списания или добавления партий при сбоях сети, эндпоинты проверяют HTTP-заголовок `Idempotency-Key`. Перед началом транзакции сервисный слой выполняет поиск этого ключа в таблице `Operation`. Если ключ уже существует для данного пользователя — транзакция прерывается, изменения откатываются, и клиенту возвращается стандартизированная ошибка `DUPLICATE_IDEMPOTENCY_KEY` со статусом `409 Conflict`. При каскадном списании дочерние логи снабжаются составными уникальными суффиксами для предотвращения ошибок уникальности на уровне СУБД.

### Обработка конкурентных запросов (Race Conditions)
Для исключения ситуаций, когда два параллельных запроса могут одновременно списать один и тот же остаток, уводя партию в минус, применена **Пессимистическая блокировка строк на уровне СУБД**. Внутри атомарного блока `@transaction.atomic` выборка активных партий выполняется через метод `.select_for_update()`. Это генерирует SQL-запрос `SELECT ... FOR UPDATE`, который монопольно блокирует строки в базе данных для текущей транзакции. Любой параллельный запрос переходит в состояние ожидания (Lock Wait) до момента коммита первого запроса.

### Работа фоновых задач
Фоновые задачи развернуты в **Celery Beat** и настроены на ежесуточный запуск (`crontab(hour=0, minute=0)`). Задача `check_expired_batches` работает идемпотентно: перед генерацией алертов о просрочке или дефиците она сверяется с логом уведомлений за текущие сутки, исключая дублирование записей. Также воркер автоматически пополняет `ShoppingItem` при обнаружении дефицита.

## 6. Известные ограничения системы
1. **Смена единиц измерения:** Система производит расчеты в рамках дефолтной единицы измерения товара (`default_unit`). Каскадная конвертация (например, автоматический перевод граммов в килограммы при списании) на уровне ядра сервиса текущей версии требует явного соответствия базовых единиц.
2. **Часовые пояса:** Все операции и даты строго пишутся и валидируются в формате UTC. Локальное время отображения должно настраиваться на стороне клиентского приложения (Frontend).
